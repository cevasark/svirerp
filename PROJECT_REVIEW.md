Review baseline: `zeffy-import-refactor`, commit `6337f15` (`Shareable deep links after login; ARCHITECTURE.md and SETUP.md`). Reviewed September 21, 2026. This report supersedes observations from the earlier branch.

> **Historical review:** This document records the September 21 baseline. The Zeffy Contacts/Transactions spreadsheet-import implementation and the findings tied to it were subsequently removed by V53. Phase 1 now uses the Zeffy API for campaign discovery and mapping; see `zeffyIntegration.md` for the current specification and `README.md` for current endpoints.

The application has a coherent foundation for incremental enhancements. Its most consequential remaining issues involve duplicate import commits, financial validation, and a few shared UI controls. A framework rewrite is not indicated by this review. Business-rule changes should follow clarification of the questions below.

The user confirmed three requirements during this review: **free Followers must keep their active status until explicitly changed; manual membership contributions, accounting, and membership recalculation are deliberately maintained separately by staff; and reuploading is the intended recovery process for failed Zeffy imports.** Accordingly, automatic synchronization and reopening failed batches are not proposed enhancements. The free-Follower recomputation defect has been corrected and covered by a regression test.

This began as a source, schema, documentation, and test review. After the singleton-organization cleanup, the backend suite completes with **67 tests passing, zero failures/errors/skips**, across 15 test classes, and the Angular production build succeeds with its existing bundle-budget warnings. No database was migrated, production service restarted, or external integration request sent. Findings below describe code paths and reproducible scenarios; they are not claims that production data has already been affected.

The declared backend is Java 25 / Spring Boot 3.5.16, with Spring Data JPA, Spring Security, Flyway, and MySQL Connector/J. `ARCHITECTURE.md` says the actual development/production database is MariaDB 11.8, while the README primarily describes MySQL. The UI declares Angular 21, Angular Material, TypeScript 5.9, RxJS, and Zone.js. Production packaging copies an independently built Angular bundle into the Spring Boot JAR; development uses an Angular proxy to preserve the same-origin session-cookie model.

The current membership rules are explicitly described in `TierCalculator.java` and covered by tests: each individual payment of at least $150 adds one year; $1,000 or more selects Benefactor, otherwise Member. Payments are sorted by date. A renewal received on or before the current expiry extends that expiry; after a lapse it starts from the payment date. The latest qualifying payment determines tier, including a downgrade from Benefactor to Member. After expiry, a paid tier is retained and status becomes inactive. Sub-$150 payment history produces an active, nonexpiring Follower. A Follower with no payments preserves the active/inactive status assigned by staff or import. These are existing requirements to preserve unless instructed otherwise, rather than defects inferred from unfamiliar business rules.

The following findings deserve attention before extending the affected workflows. Paths are relative to the repository root; line numbers refer to the reviewed commit.

1. **High: Zeffy duplicate protection does not cover commit.** Preview the same transaction in batches A and B before committing either. Both become ready; committing A does not invalidate B, and B can create another payment and journal entry. With chained renewals, a duplicated qualifying payment also adds another year. Duplicate checking occurs in `src/main/java/com/svivanrilski/svirerp/zeffyimport/ZeffyImportService.java:345`, while `ZeffyImportRowApplier.java:51` checks only that particular staged row's outcome. The dedupe index in `src/main/resources/db/migration/V41__create_zeffy_import.sql:89` is nonunique. Concurrent commits are also unprotected. Add an atomic transaction-level uniqueness/claim mechanism and commit-time validation, with tests spanning two pending batches.

2. **High: General journal posting trusts header totals rather than journal lines.** `src/main/java/com/svivanrilski/svirerp/finance/FinanceService.java:287` compares stored header debit/credit totals. Creating/deleting lines does not recalculate them, and `createEntry` at line 271 accepts an already-posted status. A draft with equal headers and unbalanced actual lines can therefore post. Standard income/expense/transfer helpers build balanced lines, but the general journal API bypasses that assurance. Derive posting totals from persisted lines and enforce posting through one operation.

3. **Resolved: Recompute All previously deactivated free Followers enrolled by People import.** `MembershipService.recomputeTier` now preserves the existing status of a Follower with no completed-payment history, while non-Followers without payments still become inactive. `MembershipServiceTierTest` covers the regression.

4. **High: Financial parsing accepts absent or malformed amounts as valid values.** Zeffy's required headers omit Amount (`ZeffyImportService.java:82`). `parseAmount` at line 544 turns a missing Amount or `unknown` into zero and `(150.00)` into positive 150. Ordinary minus-prefixed negatives are now rejected, but parenthesized negatives bypass that check. Missing dates may preview as ready and fail only at commit. Validate required monetary data explicitly and align preview validation with commit validation.

5. **High: Gmail and Calendar connection callbacks lack request/session correlation.** The custom authorization builders and callbacks in `src/main/java/com/svivanrilski/svirerp/email/GmailOAuthController.java:44` and `src/main/java/com/svivanrilski/svirerp/event/GoogleCalendarOAuthController.java:43` generate/accept no OAuth `state` and do not verify that the callback belongs to the connection attempt initiated by that administrator. Admin authentication alone does not establish that correlation. Bind the authorization response to a one-time value in the initiating session. This concerns the custom integration connections; Google sign-in itself uses Spring Security's OAuth flow. No exploit was attempted.

6. **Saved campaign membership settings can be lost on preview reload.** Saving mappings does not recompute staged outcomes. The UI starts mapping selections empty and membership unchecked, without loading saved mappings (`ui/src/app/features/finance/pages/zeffy-import-detail/zeffy-import-detail.component.ts:199`, line 250). Saving membership=true, refreshing, then reselecting a fund can overwrite the saved flag with false. Existing mappings and the membership backfill also lack an operator-facing editor/action. Make persisted mappings the source of UI state. Separately, `ZeffyImportService.java:504` closes attempted batches even with failed/unmapped rows; the user confirmed that recovery by reuploading is intentional and should be preserved.

7. **Recomputation can replace manually assigned membership status.** Payment-derived status overwrites existing status, including suspended, in `MembershipService.java:331`; there is no automatic expiry recomputation job. Clarify how suspension should interact with imported payments and the manual recompute action. In contrast, manual contribution create/update/delete at lines 242, 251, and 267 intentionally do not recompute tier or post/reverse ledger effects. The user confirmed staff maintain those records separately; preserve that separation, including for manual refund status changes.

8. **Zeffy reclassification loses the original fund tag.** `ZeffyImportRowApplier.java:191` calls `FinanceService.reclassifyIncome` at line 843 without a fund; both correcting lines omit it. A Fund F Ticket payment reclassified to Donation appears corrected organization-wide but remains Ticket revenue in Fund F's filtered category report. The fund's total balance remains correct because the correction has zero net revenue. Preserve fund attribution on correction headers/lines and a traceable correction link.

9. **Stripe recovery, dating, and concurrency have gaps.** `StripeWebhookEventApplier.java:127` dates payments and journals using the processing day, so delayed reprocessing changes both accounting date and membership period. Failed Price lookup can store a null Price ID (`StripeWebhookService.java:325`); Reprocess at line 370 does not retry that lookup, leaving such rows stuck. Concurrent reprocess requests can both pass the unlocked status check (`StripeWebhookEventApplier.java:86`). Redelivery of any existing event is ignored (`StripeWebhookService.java:121`), including a received event left unapplied by an interruption. Add integration tests around original dates, external lookup recovery, and atomic event application.

10. **Import review and entity selection have hard limits.** Zeffy detail requests only the first 200 rows and has no paginator (`zeffy-import-detail.component.ts:335`), although commit processes the whole batch. Several person/member picklists load only the first 200/500 records. Preview new-person/new-member counts count row flags rather than distinct eligible people; ordinary Ticket rows may be counted as new members even though they will not create membership. Server pagination/search and accurate eligible-record summaries are needed for trustworthy larger imports.

11. **Shared autocomplete can retain an invisible previous selection.** `ui/src/app/shared/components/autocomplete/autocomplete.component.ts:120` reacts to text edits without clearing the parent form's selected ID. Selecting person A and then editing/deleting the text can still submit A. An HTTP search error also terminates the search subscription because it lacks recovery. The default four-character minimum, combined with first-name-only queries, prevents ordinary lookup of names such as Ann or Bob. This affects trustees, volunteers, and new project/task assignees.

12. **Deployment is not reproducible from a clean checkout.** `ui/.gitignore:5` excludes the lockfile, but `redeploy.sh:70` uses `npm ci`, which requires one. The script stops the running instance before rebuilding (line 44), skips backend tests (line 74), and checks an open TCP port rather than application health. A failed install/build leaves the service stopped. Commit a reviewed dependency lockfile, build/test before stopping the service, and retain a known-good artifact for rollback. No deployment command was executed during this review.

Additional observations worth carrying into enhancement work:

- **Member CSV overwrite rules:** absent optional columns and empty cells both clear stored member number/expiry (`MembershipService.java:200`). Existing person fields are not updated. Boolean parsing treats values other than `true` as false, including `yes` and `1`. Agree whether blanks mean preserve or clear.
- **CSV/XLSX coverage:** readers do not strip a UTF-8 BOM before exact header matching. Member CSV parser iteration can fail after earlier rows have committed, outside the per-row error handler. Excel paths use the first sheet; no real XLSX fixture tests were found. Real anonymized export samples would improve compatibility testing.
- **Contact semantics:** existing People rows are skipped rather than enriched; importing Transactions first can prevent Contacts from importing their addresses or unsubscribe state later. Matching by unique email does not support independently importing people who share an address or have no email.
- **Membership boundary cases:** same-day qualifying payments have no explicit secondary ordering, although the last payment controls the tier. Future-dated qualifying payments are not excluded. A later qualifying contribution can overwrite suspended status. These need explicit policy before modification.
- **Stripe scope:** the first line-item Price classifies the entire Checkout/Invoice amount. Missing fees can fall back to gross deposits without later refresh. Refund/dispute/delayed-payment/payout flows are not implemented by the three-event receiver. Event-ticket payments do not automatically register attendees. These may be appropriate scope limits if operations account for them elsewhere.
- **Calendar consistency:** cancellation and recurrence are stored locally but not sent in the Google payload (`GoogleCalendarService.java:122`). Failed remote deletion is logged before local deletion removes the reference. Retaining a retry record would help prevent stale published events.
- **Integration reconnect behavior:** `GoogleOAuthTokenService.java:40` returns a cached access token before rereading credentials; the cache is keyed by the setting name and is not invalidated on reconnect. The documentation's immediate-rotation claim is therefore inaccurate for Gmail/Calendar. Email infrastructure currently has only the test-email caller, not implemented automatic reminders or notices.
- **Project/checklist collaboration:** server-side comment authorship is a good safeguard. Checklist target dates and project-level placement are documented choices. The service does not enforce the UI's reopen-before-changing-terminal-state convention. There is no optimistic concurrency version or general edit history; concurrent edits can overwrite each other. Project deletion cascades to tasks, comments, and checklists.
- **UI details:** pressing Enter repeatedly can submit duplicate checklist items while the button is disabled; some shared clickable elements lack keyboard link/button semantics. Import dialogs can close during an active request and lose the result report. Repeated session-expiry 401s can overwrite the saved deep link with `/login`; client auth state is not cleared on those failures.
- **Organization boundary:** resolved by V52 and the singleton profile API. The database prevents a second organization row, domain tables no longer repeat `org_id`, and `/api/organization/**` requires `ROLE_ADMIN`.
- **Migration portability:** V45 explicitly assumes historical Zeffy data was manually cleaned in the original database before its format change. Other environments retaining old import rows need a deliberate migration plan. V50, by contrast, preserves checklist data while changing its parent relationship. Applied migrations should remain immutable.

The current tests meaningfully cover import format/category/ID checks, individual row routing, tier chaining, historical join dates, income fee splits, transfers, reclassification sides, report arithmetic, person search, and Stripe applier outcomes. They are mocked service/pure-function tests. No database/Flyway integration tests, security-filter tests, Governance tests, or Angular spec files were found. They do not demonstrate transaction rollback, concurrent commits, end-to-end import correction, or actual external-service recovery.

For the first enhancement cycle, add focused tests and fix the affected operation together: duplicate pending Zeffy batches; required/invalid amounts and XLSX fixtures; corrected-file reupload and mapping reload; journal balance derived from lines; original Stripe payment dates and recovery; and fund-preserving corrections. Preserve separate manual bookkeeping and reupload-based recovery. Shared autocomplete and import pagination can be addressed independently. A CI check should run backend tests and a reproducible Angular production build before release.

The following decisions would make subsequent implementation safer and more precise:

1. Which workflows are used daily in production, what is the first enhancement priority, and what are the typical/largest people and import counts?
2. Free Followers must remain active without payment (confirmed). Should recomputation also preserve manually suspended status? Should email unsubscribe change membership activity as well as email preference?
3. Staff maintain manual contributions and accounting separately (confirmed). Is the ERP ledger the authoritative bookkeeping record or a supplementary record? Which date should delayed Stripe processing use?
4. Reuploading failed imports is intentional (confirmed). What correction/reversal workflow is needed for records that were successfully committed with the wrong amount, person, or classification?
5. Should existing contacts be updated/enrolled by Contacts import? How should shared/missing email and blank CSV update cells be handled?
6. Should every Donation and every membership-enabled Ticket grant membership credit, including repeated qualifying donations, or only specific purposes/campaigns? The renewal chaining algorithm itself is already documented as intentional.
7. Can Stripe payments contain multiple different products, and are refunds, disputes, delayed payments, or automatic attendee registration required?
8. Should the documented shared operational access remain for actions such as project deletion, and what audit/retention expectations apply? Organization profile edits are admin-only.

The existing architecture, single-organization deployment, same-origin session authentication, domain layering, Flyway ownership, explicit campaign overrides, documented renewal chaining, and the three user-confirmed requirements provide the working conventions for future changes. Other business-rule questions remain open; this report does not assume their answers or authorize changing production data.
